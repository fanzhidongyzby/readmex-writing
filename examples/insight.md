# Agent 的恢复能力：让任务在中断之后仍然连续

> 公开合成示例，仅演示给定设想怎样形成论述，不是用户真实经历或实测系统。输入见 insight-input.md；没有外部测量或性能成绩。

一个Agent能给出完整计划，和它能把工作持续做完，是两种不同的能力。连接会断，工具会失败，任务可能比一段上下文更长。对于工程系统，真正重要的往往是中断之后还能不能知道自己做到哪里，并以合理代价继续。

我想研究的，是把恢复能力从异常处理提升为Agent设计的一部分。任务不应只存在于一段对话里，而应留下能够追查、接手和验证的状态。

## 1. 进度不能只在记忆里

如果一个流程只在聊天中说“已经处理完前三份文件”，下一次执行者就需要相信这句话，或者把所有文件再检查一遍。前者可能继承错误，后者增加重复工作。对话能解释意图，却不适合独自承担任务账本。

因此，需要记录的不只是计划，还有稳定任务ID、输入版本、已完成步骤、产物位置和验证结果。执行者退出后，后来者仍能辨认哪些工作完成了，哪些仅仅被尝试过。

这会改变任务的边界。一个步骤不能以“Agent说完成了”为终点，而应以约定状态和可检查产物为终点。恢复也不再是重新讲一遍背景，而是读取目前可靠的状态，再决定下一步。

## 2. 重试需要处理副作用

有了账本，仍然不能简单地把失败步骤再执行一次。某个请求也许已经被服务端处理，只是返回时连接中断；再提交一次，可能创建重复文件或重复发送消息。缺少状态与副作用边界，恢复反而会制造新错误。

我希望把动作分成可以安全重复的读取、具有幂等标识的修改，以及必须先查询结果的外部操作。系统无法确认是否发生过副作用时，应该保留不确定状态，而不是把它改写成失败或成功。

这不是要求取消自主性，而是让自主性作用在清楚的边界之内。Agent可以选择路线、分配局部工作，但不能在没有证据时决定某笔事务已经完成。

## 3. 完成需要验证与接手

恢复到正确位置，也还不等于交付了可靠结果。一个文件可能已经生成，却不满足需求；一段代码可能写入了仓库，却没有运行通过。任务账本应把执行完成与验证完成分开。

这里的目标流程是：执行产生结构化产物，验证检查约定标准，再将可追溯结果提交给后续步骤。验证失败时，保留错误和已有证据，让任务回到可修复状态。执行者失效时，责任也应能被回收并重新认领。

目前这仍是一个待实现、待测试的设计。我不会把它写成成功率已经提高，也不能提前断言它会节省多少计算。下一步应比较正常完成、工具失败、连接中断和重复请求等情况，观察恢复是否减少错误与重复工作。

## 4. 能力也包括可靠地继续

这条路线给我一个不同的能力视角：解决问题不只依赖每一步是否聪明，也依赖状态、责任和证据能否持续连接。更强的推理可能找到好方案，可恢复的组织才能让方案在现实中断之后仍有机会完成。

如果Agent的价值最终是持续交付，就不应只评价一次回答的质量。中断后的定位、重试边界、验证与接手，也值得进入能力评价。我要寻找的是可靠求解的条件，而不是把异常处理包装成新的智能定律。
