# ReadmeX 样文风格指南

依据与样文编号见 [sample-audit.md](sample-audit.md)。以下不是官方规范。标记说明：

- 「观察」：本次样文中实际出现的写法，注明适用范围。
- 「建议」：为稳定生成草稿而制定的编辑规则，不声称是平台统计规律。
- 「边界」：不能随着风格迁移被丢掉的事实、身份或证据条件。

## 1. 共通内核：让读者尽快知道你在分享什么

### 1.1 直接进入内容，而不是给时代写序言

观察（实用类跨体裁）：资讯先交代事件，作品帖先交代工具用途，实践长帖先交代结果，观点长帖先亮出选择。S01、S04、S06、S07、S18、S24。

建议：短帖开头两句完成「对象 + 发生的事/核心问题」。深度科技洞见可先用简洁引言交代真实行业背景与问题缺口，再进入场景和判断；不写空泛时代铺垫、百科定义或连续反问。完整作者版以 editorial-profile.md 的后续校准为准。

问候、新人报到和文学表达是例外。不能把所有作品都改成论点摘要。

### 1.2 具体内容比装饰性专业感更重要

观察（技术与资讯）：工具名、运行环境、操作环节、失败表现和数据口径承担信息量，而不是密集形容词。S02、S07、S13、S16、S20、S24、S28。

建议：保留材料里的具体对象；解释一个机制，不堆十个术语。首遇不常见概念时给一句必要解释，Agent、API、Git 等可依读者背景保留原文。

边界：不替原材料增加版本号、实验规模、参数量、用户数或收益数据。没有数字也能成文。

### 1.3 一段一个动作，空行比富文本可靠

观察（跨体裁）：短段落、空行、普通文字小节、直接链接都实际存在。S02、S05、S07、S09、S11、S17、S20。

建议：社区短版保留纯文本可读性，一句短帖不拆成五个标题。完整科技图文版采用连贯段落、凝练两级目录和少量重点加粗，参考文献不编号；避免装饰性 emoji、满篇加粗、大表格和密集口号。图片及飞书排版按 illustrated-delivery.md 完成，平台 Markdown 渲染能力仍需独立确认。

边界：S03 的评论有不支持 Markdown 与长文截断的用户反馈，S05 可见正文确实在结尾截断。未核验前端、存储和 MCP 各自行为，因此不能宣称“平台禁止 Markdown”或给出精确字数上限。文案默认不依赖富文本，长稿完整保存，发布前另行检查预览。

### 1.4 提供一个可以接着聊的入口

观察（多数实用类）：实践问验收成本，求助描述卡点，观点问概念或后果，资讯 bot 统一问“你怎么看？”。S07、S09、S14、S15、S18–S32。

建议：有问题时问一个具体问题，不机械收尾。不加入“欢迎点赞关注转发”。诗歌、明确结论和单纯资源链接可以自然结束。

不能把互动形式当成有效性证据；本次样本的分数与回复量不足以证明哪种写法更受欢迎。

## 2. 两条主要路线，不要混成一种腔调

### 2.1 资讯解读：明确转述，补上意义

观察：S18–S32 为同一个 headlines bot，跨七个社区使用相近结构：

事件与关键细节。

为什么重要：与读者/产业/研究实际相关的意义。

你怎么看？

可迁移：信息先行、事实与意义分段、来源归属、限制条件。只在资讯体裁中保留“为什么重要：”这个显式标签。

不可泛化：这不是七组独立作者对同一格式的认可，更不是成员长文的统一模板。用户没有要求 bot 风格时，讨论问题可以更具体，资讯正文也不必复制固定尾句。

“为什么重要”要解释机制或实际影响，不能把首段换词再说一次。材料无法支撑时只说明直接影响，不拔高到行业重构、AGI 到来或技术革命。

### 2.2 成员实践与观点：有立场，有过程，有代价

观察：S04、S05、S07 通过具体选择、反面情况和适用范围推进论证；S02、S13、S14 则是更短的经验与工作流分享。

可迁移：先说结果或选择，写具体做法，承认代价，落在个人判断。可以口语化，可以明确表达偏好，不必变成中立新闻摘要。

不可泛化：S04、S05 出自同一作者，锋利的比喻和绝对句不应成为全平台共性。只迁移“判断 → 理由 → 边界”，不复制独特修辞或其投资判断。

边界：有“我做过”的材料才写复盘。没有实践时写“我想试一种做法”，不写“后来发现”“上线后”“实测证明”。

## 3. 按体裁组织

### 资讯

- 标题：主体 + 行动/变化 + 必要限定。例如“某工具开放研究预览”，不要写成“某工具正式上线”。
- 正文：来源、事件、2–4 个最关键细节、可用范围和未验证部分。
- 意义：对谁、在哪个环节、为什么有影响。
- 来源：材料包含的真实链接，必要时用“据报道”“官方称”。不造一级来源。

### 实践

- 开头：结果或当前状态 + 项目/场景。
- 中段：做法与分工，沿实际流程讲，不给每个段落都套“背景/挑战/解决方案”。
- 结果：成功与失败一起保留，数量、环境和时间口径一致。
- 收尾：可复用的判断，或一个关于具体环节的问题。

### 观点或未验证方案

- 开头：一个可讨论的判断或问题。
- 中段：为什么这样想，机制是什么，与另一种选择差在哪。
- 边界：什么情况不成立、哪些前提未验证。
- 收尾：下一步如何判断，或读者能提供哪种经验。

材料很少就写短，不把两句话扩成假装有证据的长文。材料扎实时可以有长论证，但避免只用“不是 X，而是 Y”反复制造张力。

### 资源分享与求助

资源：是什么 → 能帮谁做什么 → 怎么找到。S01、S06、S17。

求助：环境 → 预期 → 实际表现 → 已试办法 → 精确问题。部分样文没有这么完整，这是编辑建议，不是强制补造细节。

代码、文档、书籍的链接不自动等于有效、合规或可访问；不为补稿下载未提供的书籍全文，也不扩散材料里的秘密。

### 创作与随想

S11、S12 是短诗；S09、S10、S15 是概念与社会议题的讨论，不能把它们混成一类。

诗歌保留意象、节奏和留白，不增加“为什么重要”、数据、来源或问答尾巴。随想可短而直接，观点可以尖锐，但不能将隐喻写成实证结论。

## 4. 写法与可信度是两件事

以下是编辑边界，不是断言所有样文都做得正确：

| 材料中的说法 | 草稿应怎么处理 |
|---|---|
| 官方自测领先 | 归属到官方及具体基准，不写成独立证明 |
| Oracle CER lower bound | 理想选择条件下的理论下界，不写成融合系统已达到的错误率 |
| 50 次、固定子样本、特定硬件 | 保留样本和环境，不外推到所有任务/设备 |
| 厂商承诺将开源 | 保留计划时态，不写成已公开权重 |
| 锁定对话、访问控制 | 不升级为端到端加密或“不上传数据” |
| 回测有效 | 不等同于实盘收益，保留成本与样本边界 |
| 有投诉、有调查 | 不写成已经违法或事实定论 |
| 一次反例/个人体验 | 可以支持个人判断，不据此宣布行业规律 |

S16 的正文把理论下界写得很像实际最低错误率；S05 的成本举例也不能被当成通用投资结论。学习样文结构，不复制其可能的概念或计算问题。

## 5. 自查中的删改标准

删除：时代铺垫、无依据夸张、空泛总结、机械互动、与主题无关的营销词。

保留：用户主张、具体步骤、关键数字口径、失败案例、反例、条件和可公开来源。

改写：把“已证明”恢复到“官方称/作者报告/尚待验证”；把编造的第一人称经历恢复到计划或第三人称；把漂亮但不确定的标题改为与正文同等确定。

不要为了“社区风格”削平用户个性，也不要用长篇免责声明盖住内容。限制紧跟相关结论写清楚即可。
