# 输入到草稿示例

以下全部是为检验本 skill 原创的示范输入与草稿，不是社区原帖，也不是用户真实项目或已核验新闻。示范数据仅在各自输入设定内成立。迁移结构，不将示范事实带入实际写稿。

## 示例 A：只有想法，写成方案讨论

### 输入

目标社区：rsi。

我想让智能体每次任务后整理失败原因，提出一个提示词修改。先做离线比较，效果更好才保留，否则回退。还没实现，也没跑评测。我担心不断修改会让原本稳定的行为退化。希望讨论怎么验收。

### 草稿

让智能体改提示词之前，先把验收和回退想清楚

我想试一个比较克制的自改进循环：每次任务结束后，先整理失败原因，再提出一个提示词修改。改动先做离线比较，效果更好才保留，否则回退。

我在意的不是它能不能写出新提示词，而是这次修改到底修好了什么。

一个担心是，修改对刚才失败的任务有帮助，却让原本稳定的行为退化。如果只看最近一次结果，很容易把“对这道题更好”当成“整体更好”。

所以，验收至少要回答两个问题：原来的失败有没有改善，原来能稳定完成的任务有没有被破坏。没有这两个判断，提示词改得越勤，未必越可靠。

目前这还是一个未实现、未评测的方案。下一步我想先确定离线比较的任务集合和保留标准，再考虑让循环自动运行。

如果你做过类似尝试，会怎样选验收任务，避免修改只适合刚刚失败的那一次？

### 检查点

- 没写“系统已经进化”“实测提升”。
- 新增的验收建议被写成推理与计划，不是已做实验。
- `rsi` 使用主题适配建议，不宣称复制其既有文章风格。

## 示例 B：有过程与失败，写成实践复盘

### 输入

做了一个本地文档分类脚本。原始文件只读，分类结果存到另一个目录。先只按标题分类，抽查20份PDF，有7份分错；后来加入正文开头5段，同一批有3份分错。失败集中在标题很泛、前几段都是背景的文档。没有速度数据，没有更大测试集，也没上线。语气自然，不要宣传。

### 草稿

文档分类不能只看标题，但多看一点正文也不是万能的

做了一个本地文档分类脚本，先拿 20 份 PDF 做抽查。只按标题分类时有 7 份分错；加入正文开头 5 段后，同一批还有 3 份分错。

目前这个结果只能说明：在这批文档里，多看一点正文比只看标题更有帮助，不能据此判断它在更大规模材料上的表现。

怎么做的

原始文件保持只读，分类结果另存到一个目录。第一版只使用标题，后来把正文开头 5 段也加进分类依据。

这样改的原因很直接：有些标题太泛，单看标题很难判断文档真正讨论什么。

剩下的坑

加入正文之后仍然有错误。失败主要集中在标题很泛、前几段又都在讲背景的文档，真正的主题还没有出现。

这也提醒我，问题不只是“读得少”，还包括“读到的部分有没有信息”。把开头固定多读几段，不一定就能得到真正有用的依据。

当前边界

测试只覆盖同一批 20 份 PDF，还没有更大的测试集，也没有速度数据和上线验证。现在能说的是，这次改动减少了这批材料里的分类错误，不是分类问题已经解决。

你们做文档分类时，会优先选标题、摘要，还是正文中更靠近主题的片段？

### 检查点

- 20、7、3 与正文 5 段均来自示范输入。
- 没增加“提速”“达到生产可用”“用户反馈”。
- 同一批样本的结果与泛化能力分开，失败表现保留。

## 示例 C：理论下界，不能写成实测成绩

### 输入

目标社区：asr。

测试输出里有 Oracle CER lower bound: 2.18%。我想用多个语音识别模型融合，但融合算法还没实现，也没有系统的实测 CER。想讲清楚为什么值得试。

### 草稿

多模型语音识别值得试，但 Oracle 下界不是融合成绩

测试输出里的 Oracle CER lower bound 是 2.18%。这个数字让我想试多模型融合，但它不是融合系统已经达到的错误率。

Oracle 下界对应理想选择条件：如果能知道候选结果中哪些部分更接近真实答案，就能估计这组候选还有多少可利用空间。真实系统并不知道标准答案，关键是怎样在不同输出之间作出选择。

所以，对我来说，这个数字更适合用来判断“有没有尝试融合的空间”，而不是对外报告“错误率已经降到 2.18%”。

目前融合算法还没实现，也没有系统级实测 CER。接下来需要验证的是：实际选择方法能利用多少候选差异，最终效果离这个下界还有多远。

有做过多模型融合的朋友吗？你们更依赖模型置信度、候选一致性，还是额外的纠错与选择步骤？

待确认（不属于正文）

- 若要作为实验分享发布，补充测试集、CER 计算方式和 Oracle 选择的具体定义。

### 检查点

- 没将 2.18% 写成已经实现的结果。
- 对 Oracle 的解释没有冒充这份未提供的测试代码的精确定义。
- 缺少定义与测量方法在稿外注明，正文仍可完整阅读。

## 示例 D：发布材料，保留预览状态与来源限制

### 输入

目标社区：ai_products。

用户粘贴的某工具发布说明：开放研究预览，只能邀请试用；可以跨应用整理信息；发送消息前会让人确认；没有公开稳定性测试。没有提供公开链接。写资讯短帖，不要说正式上线。

### 草稿

某工具开放研究预览，跨应用整理仍保留发送确认

据发布说明，某工具开放了邀请制研究预览，可以跨应用整理信息，并在发送消息前要求用户确认。目前尚未提供公开的稳定性测试，不能据此判断长期使用的可靠性。

为什么重要：整理信息和发送消息是两类不同动作。前者帮助用户组织材料，后者会影响外部对象；把发送确认保留下来，可以让用户在信息真正发出前检查内容。

当前更值得观察的是，它能否在真实工作流里把信息整理正确，而不只是完成一次演示。

你会把哪一类跨应用整理任务交给这样的预览工具？哪些内容必须自己检查？

待确认（不属于正文）

- 补充工具名称与可公开的发布说明链接；本稿仅依据粘贴材料，未外部核验。

### 检查点

- “研究预览”“邀请制”“未提供公开测试”都保留。
- 没造链接，没说已经读过官方网页。
- “为什么重要”解释动作边界，而不是复述功能列表。
